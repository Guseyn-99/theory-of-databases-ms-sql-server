## Задача 4.3. TABLOCKX

Логика: Явная монопольная блокировка всей таблицы. Сравниваем с обычным UPDATE по уровню параллелизма.

Обычный UPDATE — блокирует только изменяемые строки (4 записи), остальные данные доступны другим сессиям.

![Скриншот](screenshots/28.png)

UPDATE с TABLOCKX — блокирует всю таблицу Students монопольно. Транзакция не закрыта, поэтому блокировка удерживается.

![Скриншот](screenshots/29.png)

Проверка блокировки — SELECT из второго окна завис, потому что TABLOCKX не даёт читать таблицу, пока транзакция открыта.

![Скриншот](screenshots/30.png)

COMMIT — блокировка TABLOCKX снята, транзакция завершена.

![Скриншот](screenshots/31.png)

Разблокировка — второй SELECT мгновенно выполнился, таблица снова доступна для чтения.

Ожидаемый результат:Одна из сессий должна была получить ошибку 1205 и стать «жертвой deadlock».

Фактический результат:Deadlock воспроизвести не удалось. Обе сессии завершились успешно.

Причина:Окна SSMS подключены к одному экземпляру SQL Server, но запросы выполняются последовательно, а не параллельно. Даже при визуально быстром запуске (F5 → переключение вкладки → F5), SQL Server выполняет их по очереди. Время завершения сессий подтверждает это: разница между ними всегда равна значению WAITFOR DELAY (10)

## Задача 7.1. Процедура выставления оценки (вложенные транзакции)

Логика: Внешняя транзакция вызывает процедуру, которая открывает свою транзакцию. Внутренний COMMIT уменьшает @@TRANCOUNT только на 1 — до уровня внешней транзакции. Реальный коммит происходит только когда внешняя транзакция тоже закоммитит.

## Задача 7.2. Откат вложенной транзакции

Логика: ROLLBACK внутри вложенной транзакции (в процедуре) откатывает всю транзакцию целиком, включая внешнюю. Это ключевое отличие ROLLBACK от COMMIT.

![Скриншот](screenshots/48.png)

## Вызываем из внешней транзакции с проверкой

![Скриншот](screenshots/49.png)

Вывод: COMMIT внутри вложенной транзакции — это «мягкий» коммит (уменьшает счётчик). А ROLLBACK — «жёсткий»: он откатывает всё, включая внешнюю транзакцию. Поэтому вложенные транзакции нужно использовать аккуратно: одна ошибка внутри процедуры может откатить всю работу внешнего кода.

## Задача 7.3. Безопасный шаблон вложенных транзакций

Логика: Процедура запоминает исходный @@TRANCOUNT. Если транзакция уже открыта извне — она не открывает свою и не коммитит. Так процедуру можно безопасно вызывать и отдельно, и внутри другой транзакции.
